Hcp::Visit

Visits

One stop of a job: when the work is booked to happen, where the job does.

Housecall Pro calls a visit an appointment and files it inside a job, so the visits booked within a window are read off the jobs booked across it. Each says what its job says, and carries the job along.

A job is accepted once and visited as often as the work needs. Most jobs are one trip, and then the job and its visit say the same thing; the rest are the reason a visit is a record of its own.

Reading visits

#

The visits booked to start within a window are walked off the account, the same way the jobs are:

account.visits.upcoming(2.weeks).each do |visit|
  visit.id, visit.description, visit.starts_at, visit.ends_at, visit.anytime?
  visit.job              # => the Hcp::Job the stop belongs to, its place along
end

upcoming looks ahead from now and past looks back, and each takes how far — a duration in Rails, a number of seconds outside it, or nothing at all. Both ends are measured from one moment, so nothing slides between them:

account.visits.upcoming 2.weeks # booked to start between now and two weeks on
account.visits.past 4.weeks     # booked to start between four weeks ago and now
account.visits.upcoming         # every visit to come

The list is Enumerable, so everything Enumerable answers, it answers:

account.visits.upcoming(2.weeks).map &:starts_at
# => [2026-06-26 10:45:00 UTC, 2026-07-02 09:00:00 UTC]

account.visits.upcoming(2.weeks).first # => the next stop, or nil where none is booked
account.visits.upcoming(2.weeks).ids   # => every ID, the list walked

Read off the jobs, not off a list of their own

#

Housecall Pro answers no list of appointments. It files each one inside the job it belongs to, and sends them beside a job only where the list asked it to. So the visits in a window are read off the jobs booked across it, a page of jobs at a time, with their appointments asked for:

account.visits.upcoming 2.weeks
# one walk of the jobs whose booking overlaps the window, appointments and all,
# and each job's stops handed back as they arrive

Three things follow from that, and each of them is a decision rather than an accident:

A job booked across the window is read whole. Its booking may start before the window and end after it, and the stop inside the window still belongs to it. So the jobs asked for are the ones whose booking overlaps the window — those still running when it opens, and those already begun when it closes — and each stop is then kept only where it starts inside the window.

A canceled job keeps its visits to itself. Where the customer or the pro called the job off, its stops are not walked — nobody is coming.

A list nothing narrows walks every job there was. account.visits.upcoming with no window reads the whole account, one page of jobs at a time. Name a window where the account is large.

What a visit reads

# 
visit = account.visits.upcoming(2.weeks).first

visit.id          # => 'appt_02aad0c5d573454cae36e5fa24c839bc'
visit.description # => 'Exterior trim - Fascia repair'
visit.starts_at   # => 2026-06-26 10:45:00 UTC
visit.ends_at     # => 2026-06-26 12:45:00 UTC
visit.anytime?    # => false

anytime? is what tells a booked day from a booked time. Where it is true, the customer was given a date and no hour, and the two moments are the day rather than a window inside it.

An appointment has no words of its own on Housecall Pro, so description is the job's. That is the vocabulary's answer to a stop nobody named: it says what the visit is for, rather than nothing at all.

The job it belongs to

#

A visit came off a job, so it hands the whole job back rather than an ID to go and read one by. Nothing is fetched for it — the job is already in hand, its location and its customer with it:

visit.job.id                    # => 'job_77cbcb51acb1442fa9554131d7d1f543'
visit.job.amount                # => 0.33e3
visit.job.location.city         # => 'Springfield'
visit.job.location.customer.phone # => '5550000001'

That is the round trip a dispatcher wants: where to be, when, and whom to call on the way. The job's own page has the rest of what it reads, and its lines and quote still cost a request each on the first ask.

What a visit does not do

#

Booking a stop, moving one and calling one off all happen in Housecall Pro. This gem takes no write for a visit, so Hcp::Visit has no create, no update and no destroy, and no way to read one by its ID.

Housecall Pro sends no names with a stop, only IDs for the pros dispatched to it, and the vocabulary has no word for a pro, so the gem reads none. What a visit is for reads off its job.
