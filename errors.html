Two kinds of refusal live here: the ones Housecall Pro sends back, and the ones the gem raises before a request goes out because Housecall Pro would have answered them with the wrong thing.

Three classes, one rescue

#

Everything this gem raises descends from Hcp::Error, so one rescue still catches the lot — including anything a later release adds.

What the gem raises
ClassDescends fromRaised where
Hcp::ErrorStandardErrorHousecall Pro would not answer
Hcp::NotFoundHcp::ErrorHousecall Pro has no record under that ID
Hcp::TooManyRequestsHcp::ErrorHousecall Pro refused the request for rate
 
begin
  Hcp::Job.find 'job_nope'
rescue Hcp::NotFound
  nil
rescue Hcp::Error => error
  error.message # => what Housecall Pro said
end

Housecall Pro writes a refusal three ways — the message under an error, the message as the error, and the message on its own. All three read as error.message.

Rate limits

#

Hcp::TooManyRequests carries the moment the limit lifts, where Housecall Pro named one in its RateLimit-Reset header:

begin
  Hcp::Job.all.each { |job| puts job.description }
rescue Hcp::TooManyRequests => error
  error.reset_at # => 2026-08-25 18:40:00 UTC, or nil
end

Nothing here sleeps. A caller told to come back later has a queue that can bring the whole job back, which is worth more than a worker asleep holding a connection open. Reschedule on reset_at, and where it is nil, on whatever your queue's backoff would have chosen anyway.

Refused before it is sent

#

Housecall Pro answers a condition it does not take by ignoring it and handing back the whole account. That is a plausible wrong answer, which is the worst kind, so the gem refuses one here where it can still be named. Every message below is raised without a request going out.

A condition, an order or an expansion the resource does not have:

Hcp::Job.where bogus: 1
# => Hcp::Error: bogus is not one of: scheduled_at, ends_at, customer_id,
#    employee_ids, work_status, location_ids

Hcp::Job.order bogus: :desc
# => Hcp::Error: bogus is not one of: created_at, updated_at, invoice_number,
#    id, description, work_status

Hcp::Job.includes :bogus
# => Hcp::Error: bogus is not one of: attachments, appointments

Hcp::Customer.where email: 'ada@example.com'
# => Hcp::Error: email is not one of: q, location_ids

A name is refused as the chain is built. A range is refused as the list is read, since that is when it is turned into parameters — still before the request goes out, and still by name.

A range where Housecall Pro takes one value, because there is no second parameter to send the other end as:

Hcp::Customer.where(q: 'a'..'z').first
# => Hcp::Error: q takes one value, not a range

A range that excludes its end. Housecall Pro reads both ends inclusively, so the record on the boundary would come back anyway and the range would have promised something it did not do:

Hcp::Job.where(scheduled_at: 1.week.ago...Time.now).first
# => Hcp::Error: scheduled_start_max cannot exclude its end

Hcp::Job.where scheduled_at: 1.week.ago...   # fine: no end to exclude

What each resource may be narrowed, ordered and expanded by is on its own page: jobs, customers, estimates.

On the two writes

#

Leads raise the same Hcp::Error, and raise it for one more reason: a connection Housecall Pro will not take. Both Hcp::Lead#create and Hcp::Lead::Pipeline#update turn a refused connection into the same class as a refused request, so a caller has one thing to rescue rather than two:

begin
  Hcp::Lead::Pipeline.new(id: id, key: key, company_id: company_id).
    update status_name: 'Won'
rescue Hcp::Error => error
  error.message
  # => 'Status Won not found for lead lea_9f0a1c8d2b4e4f0f8c1d2e3f4a5b6c7d'
end

What is not an error

#

A record Housecall Pro holds nothing for is not a refusal. A field it never answered reads as nil, a list it never answered reads as [], and neither raises:

Hcp::Job.first.completed_at # => nil, on a job that is not finished
Hcp::Job.first.tags         # => [], on a job that is tagged with nothing
Hcp::Customer.where(q: 'nobody').first # => nil, where the search matched none

find is the one that raises, because an ID names a record a caller believes exists. A search that matches nothing simply matched nothing.
