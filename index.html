hcp

A Ruby client for the Housecall Pro API.

Set a key once, name a location per call, and read a Housecall Pro account the way you read a database: where, order, limit, includes, find. It needs the standard library and three files of Active Support, to tell a field Housecall Pro answered empty from one it never answered at all.

Every method in this gem is one Housecall Pro endpoint. Where Housecall Pro has no endpoint, this gem has no method — so a resource answers update only where Housecall Pro takes a PUT, and a job, which it takes none for, answers none. Version 1.4.0 reads. Writing — beyond the leads that were here before it — comes next.

How to install

# 
gem install hcp

Or, in a Gemfile, pinned to the current major:

gem 'hcp', '~> 1.4'

~> major.minor means bundle update never crosses a breaking change. The gem asks for Ruby 3.2 or later, and for Active Support — three files of it, not the whole of it.

The key, and the location

#

Set the key once. Left unset, the gem reads HCP_KEY from the environment, so a deployment that already carries the variable needs no line of setup at all.

Hcp.key = ENV['HCP_KEY']
Hcp.key # => 'a1b2c3d4e5f60718293a4b5c6d7e8f90'

An account with more than one location passes company_id: per call, since one process may serve several. Every entry point takes it, and every record read through one remembers it, so a job read as a location reaches its appointments as that same location:

company_id = '143e13ab-943d-483b-b9f9-14821c53c849'

Hcp::Job.find 'job_77cbcb51acb1442fa9554131d7d1f543', company_id: company_id
Hcp::Job.all(company_id: company_id).where work_status: :scheduled
Hcp::Customer.count company_id: company_id

An account with one location passes nothing, and the gem sends no X-Company-Id header at all.

A process serving several accounts hands each thread its own key for as long as a block runs, and is handed back the account that key opens. Neither thread sees the other's key, and the one set before the block comes back after it:

Hcp.with_key(key, company_id: location_id) do |access|
  access.account.name  # the location, as Hcp::Company.current would read it
  Hcp::Job.limit 10    # every read inside the block is this key's
end

Reading

#

Every queryable resource — jobs, customers and estimates — answers the same eight entry points:

Hcp::Job.all                  # every job the location holds
Hcp::Job.find id              # one job, by the ID Housecall Pro files it under
Hcp::Job.first                # the first job, or nil where there is none
Hcp::Job.count                # => 3272
Hcp::Job.limit 50             # at most fifty
Hcp::Job.order updated_at: :desc
Hcp::Job.where work_status: :scheduled
Hcp::Job.includes :appointments

All but find, first and count hand back an Hcp::Relation, which chains and which has read nothing yet:

Hcp::Job.where(customer_id: id).order(created_at: :asc).limit 10

A list is walked lazily, a page read only once the one before it runs out, so asking for three records costs one request rather than all of them. A relation is Enumerable, so everything Enumerable answers, it answers:

Hcp::Job.limit(3).map &:description
# => ['Exterior trim - Fascia repair', 'Water heater flush', 'Drain snake']

Hcp::Job.all.each { |job| puts job.invoice_number }
Hcp::Job.all.each # => an Enumerator, where it is walked without a block

Counting does not walk. A page of one carries the total beside it, so count is one small read however long the list is — and a counted limit never claims more than it would hand back:

Hcp::Job.all.count      # => 3272
Hcp::Job.limit(5).count # => 5

Conditions written as a range

#

A condition written as a range is sent as the two ends Housecall Pro takes, and an end left open is left out:

Hcp::Job.where scheduled_at: 2.days.ago..   # scheduled_start_min
Hcp::Job.where scheduled_at: ..2.days.ago   # scheduled_start_max
Hcp::Job.where scheduled_at: 1.week.ago..Time.now

A Time is stamped in UTC and a Date is stamped as a day. Outside Rails, where 2.days.ago is not a method, a plain Time reads the same:

Hcp::Job.where scheduled_at: (Time.now - 172_800)..

Housecall Pro reads both ends inclusively, so a range that excludes its end is refused here rather than sent under a promise the API will not keep. The refusals are all in one place.

What is refused before it is sent

#

Housecall Pro answers a condition it does not take by ignoring it and handing back the whole account. That is the worst kind of wrong answer — a plausible one — so an unknown condition, order or expansion is refused here, where it can still be named:

Hcp::Job.where bogus: 1
# => Hcp::Error: bogus is not one of: scheduled_at, ends_at, customer_id,
#    employee_ids, work_status, location_ids

What each resource may be narrowed, ordered and expanded by is on that resource's own page, and every refusal is on the errors page.

Money, and the words for a status

#

Housecall Pro counts money in cents. This gem reads it in dollars, as a BigDecimal, so nothing rounds on the way through:

job.total_amount        # => 0.33e3, a BigDecimal — $330.00
job.outstanding_balance # => 0.33e3
job.total_amount.class  # => BigDecimal

Housecall Pro narrows a list by one set of words and answers with another. This gem speaks the narrower's words on both sides, so a caller never holds two vocabularies for one idea:

Hcp::Job.where work_status: :in_progress
job.work_status # => :in_progress, not 'in progress'

Every resource

#

Three resources are read from the top. The rest are reached through one of them, and are handed back already read.

  • Jobs

    Work a Housecall Pro user accepted: what it is, who it is for, and what it comes to. Hcp::Job

  • Customers

    Whoever the work is for, and the addresses they are billed and served at. Hcp::Customer

  • Estimates

    Work a Housecall Pro user offered to do, priced as one option or several. Hcp::Estimate

  • Appointments

    The visits a job is booked for, where the work takes more than one trip. Hcp::Job::Appointment

  • Records

    Addresses, employees, schedules, line items, notes, invoices and estimate options.

  • Leads

    Opening a lead, and moving one through the pipeline. The only two writes the gem has. Hcp::Lead

  • Events

    Reading a webhook payload, without reaching the network for anything. Hcp::Event

  • Errors

    What is raised, when, and what it carries. Hcp::Error

That is the whole of it. The install notes, the changelog and the test suite live upstream, and every method on every page carries a one-line description in the API reference.
