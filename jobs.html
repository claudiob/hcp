Work a Housecall Pro user accepted: what it is, who it is for, and what it comes to.

A job is the busiest record Housecall Pro holds, and the one most of a Housecall Pro account hangs off. This gem reads the part of it the company vocabulary has a word for, and reads it the way every other adapter of the vocabulary does. Everything on this page reads — the API takes no write for a job, so the gem has none.

Reading jobs

#

The jobs booked to start within a window are walked a page at a time, each read flat and in dollars however Housecall Pro nested it or counted it:

account.jobs.past(4.weeks).each do |job|
  job.id, job.description, job.created_at, job.scheduled_at, job.completed_at
  job.notes             # => "- Gate code 1234\n- Dog in the yard", one to a line
  job.amount            # => 330.0, dollars as a BigDecimal, where Housecall Pro said 33000
  job.quote             # => an Hcp::Quote, the estimate option it came from, or nil
  job.quote.amount      # => that option's total in dollars, found among the estimates
  job.location          # => an Hcp::Location, or nil where the job is booked nowhere
  job.location.customer # => an Hcp::Customer: id, name, surname, email, phone
  job.lines             # => Hcp::Line, read off the job's own endpoint on first ask
end

account.jobs is Enumerable, so everything Enumerable answers, it answers. Nothing is read until the walk starts, and a page — two hundred jobs, the most Housecall Pro hands over at once — only once the one before it runs out:

account.jobs.past(4.weeks).map &:description
# => ['Exterior trim - Fascia repair', 'Water heater flush', 'Drain snake']

account.jobs.past(4.weeks).first # => one job, or nil where none was booked
account.jobs.past(4.weeks).ids   # => every ID, the list walked
account.jobs.past(4.weeks).each  # => an Enumerator, where it is walked without a block

The window

#

A list of jobs is narrowed to one thing: when the work is booked to start. past looks back from now and upcoming looks ahead, and each takes how far:

account.jobs.past 4.weeks     # booked to start between four weeks ago and now
account.jobs.upcoming 2.weeks # booked to start between now and two weeks on
account.jobs.past             # booked to start any time up to now
account.jobs.upcoming         # booked to start any time from now on

Both ends are measured from one moment, so nothing slides between them. The two are sent as the two ends Housecall Pro takes, scheduled_start_min and scheduled_start_max, and an end left open is left out. Outside Rails, where 4.weeks is not a method, a number of seconds reads the same:

account.jobs.past 2_419_200

That is the whole of the narrowing. There is no condition on a customer, a pro or a status, no order, no limit and no reading of a job by its ID — the vocabulary has no word for them, and Housecall Pro is asked for exactly what the vocabulary reads.

What a job reads

# 
job = account.jobs.past(4.weeks).first

job.id          # => 'job_77cbcb51acb1442fa9554131d7d1f543'
job.description # => 'Exterior trim - Fascia repair'
job.notes       # => "- Gate code 1234\n- Dog in the yard", or nil where none was written
job.amount      # => 0.33e3, a BigDecimal — $330.00

Housecall Pro counts money in cents. This gem reads it in dollars, as a BigDecimal, so nothing rounds on the way through. Housecall Pro files the notes on a job one by one, and a caller wants the notes: they read as one string, one to a line, and as nil where none was written.

When the work happens

#

Housecall Pro nests when the work is booked under a schedule and when it was done under its timestamps. The job reads both flat, the way the vocabulary reads one:

job.created_at   # => 2026-06-21 13:45:35 UTC
job.scheduled_at # => 2026-06-26 10:45:00 UTC, or nil on a job that has never been booked
job.completed_at # => 2026-06-26 12:45:00 UTC, or nil on a job that is not finished

Every moment is a Time in UTC, or nil where Housecall Pro has stamped none. The trips it takes to do the work are visits, and have a page of their own.

What hangs off a job

#

Housecall Pro files the address and the customer side by side under the job. The vocabulary reads a location, whose place it is beside it, so the two arrive inside the job already answered and cost nothing more:

job.location.street        # => '1 Example Street'
job.location.city          # => 'Springfield'
job.location.zip           # => '90210'
job.location.latitude      # => 34.0
job.location.longitude     # => -118.0

job.location.customer.name    # => 'Ada'
job.location.customer.surname # => 'Lovelace'
job.location.customer.email   # => 'ada@example.com'
job.location.customer.phone   # => '5550000001'

location is nil where the job is booked nowhere, so reach for it the way you would any other record that may not be there. A customer's name is their first name, or the business's where a person has none, and their phone is the first of the mobile, home and work numbers that can be dialed, as ten digits.

Two more live elsewhere on Housecall Pro, and are read once, on the first ask:

job.lines.map &:name     # => ['Exterior trim - Fascia repair'], one request
job.lines.sum &:amount   # => 0.33e3, and no second request

job.quote                # => an Hcp::Quote, or nil where the job was won without one
job.quote.id             # => 'est_7e935e461264420eb5d6d5421558d9a3', already in hand
job.quote.amount         # => 0.145e4, one request, found among the customer's estimates

Housecall Pro files a job's lines under their own endpoint rather than beside the job, so lines is one request per job and an array afterwards. It names the estimate option a job was created from beside the job and prices it only among the customer's estimates, so quote.amount is one request per quote, and nil where the option is not found there. Each record is documented on the records page.

What a job does not do

#

Housecall Pro takes no PUT, POST or DELETE for a job, so Hcp::Job has no create, no update and no destroy. It reads. The only two writes the gem has are on leads.

Nor is a job read by its ID. A webhook that names one, as an event does, names what happened; the job itself comes round in account.jobs when its window does.
