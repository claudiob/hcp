Hcp::Job

Jobs

Work a Housecall Pro user accepted: what it is, who it is for, and what it comes to.

A job is read from the top, narrowed by six conditions, put in order of any of six columns, and handed back with its customer, its address, its notes and the pros it is assigned to already inside it.

A job is the busiest record Housecall Pro holds, and the one most of a Housecall Pro account hangs off. Everything on this page reads — the API takes no write for a job, so the gem has none.

Reading jobs

#

Hcp::Job is read from the top. Every entry point takes company_id:, and every one but find, first and count hands back a relation that has read nothing yet.

Hcp::Job.all
Hcp::Job.find 'job_77cbcb51acb1442fa9554131d7d1f543'
Hcp::Job.first
Hcp::Job.count  # => 3272
Hcp::Job.limit 50
Hcp::Job.order updated_at: :desc
Hcp::Job.where work_status: :scheduled
Hcp::Job.includes :appointments

With a location named:

company_id = '143e13ab-943d-483b-b9f9-14821c53c849'

Hcp::Job.find 'job_77cbcb51acb1442fa9554131d7d1f543', company_id: company_id
Hcp::Job.all(company_id: company_id).order updated_at: :desc
Hcp::Job.limit 50, company_id: company_id

Housecall Pro files a job under an ID beginning job_, and find raises Hcp::NotFound where it holds none.

Narrowing a list of jobs

#

Six conditions, and nothing else. What Housecall Pro takes as two parameters — a floor and a ceiling — is written here as one range.

Hcp::Job::FILTERS
ConditionWhat Housecall Pro takesValue
scheduled_atscheduled_start_min, scheduled_start_maxone moment, or a range
ends_atscheduled_end_min, scheduled_end_maxone moment, or a range
customer_idcustomer_idone ID
employee_idsemployee_idsone, or several
work_statuswork_statusone, or several
location_idslocation_idsone, or several
 
Hcp::Job.where work_status: :scheduled
Hcp::Job.where work_status: [ :scheduled, :in_progress ]
Hcp::Job.where customer_id: 'cus_06411f4c8ede416ba55bfc0604fa4f2d'
Hcp::Job.where employee_ids: 'pro_738721e93c12463ea2e756267f5a5fe7'
Hcp::Job.where scheduled_at: 2.days.ago..
Hcp::Job.where scheduled_at: 1.week.ago..Time.now
Hcp::Job.where(customer_id: id).order(created_at: :asc).limit 10

The last three of the six — employee_ids, work_status and location_ids — are the ones Housecall Pro takes more than one of, so a single value is wrapped in an array on the way out and a bare string works as well as a list of them. That set is Hcp::Job::MANY.

Chaining merges. Two calls to where narrow by both, and the second wins where they name the same condition:

Hcp::Job.where(work_status: :scheduled).where scheduled_at: 2.days.ago..

A condition Housecall Pro does not take is refused before the request goes out, rather than ignored by Housecall Pro and answered with the whole account:

Hcp::Job.where bogus: 1
# => Hcp::Error: bogus is not one of: scheduled_at, ends_at, customer_id,
#    employee_ids, work_status, location_ids

#

Housecall Pro puts a list in order of one column, so order takes one pair and a second call replaces the first rather than adding to it.

Bringing more back

#

Nothing comes back unasked. includes asks Housecall Pro for what it otherwise leaves out of a job.

Hcp::Job::EXPANDS
ExpansionWhat it brings back
:appointmentsthe visits, read off job.schedule.appointments
:attachmentswhat is filed against the job

A job read without the expansion carries no visits inside its schedule — none of them, rather than none at all:

job = Hcp::Job.includes(:appointments).first
job.schedule.appointments.map &:starts_at
# => [2026-06-26 10:45:00 UTC]

Hcp::Job.first.schedule.appointments # => []

That is one request for a page of jobs and their visits together. job.appointments is the other way to the same records, and costs a request of its own for each job.

This release reads no attachments, so includes(:attachments) asks for them and nothing on Hcp::Job hands them back yet.

What a job reads

# 
job = Hcp::Job.find 'job_77cbcb51acb1442fa9554131d7d1f543'

job.id                   # => 'job_77cbcb51acb1442fa9554131d7d1f543'
job.description          # => 'Exterior trim - Fascia repair'
job.invoice_number       # => '51575153'
job.lead_source          # => 'HouseAccount', or nil
job.original_estimate_id # => the estimate the job was won with, or nil
job.tags                 # => ['Warranty']

Money, in dollars, as a BigDecimal — Housecall Pro counts it in cents:

job.subtotal            # => 0.33e3, a BigDecimal — $330.00
job.total_amount        # => 0.33e3
job.outstanding_balance # => 0.33e3

Where Housecall Pro files the job in its own workflow. A rating is not a status, so it reads beside one rather than inside it:

job.work_status # => :scheduled
job.rated?      # => false

When the work happens

#

When the job is booked for, read off its schedule, and the moments Housecall Pro stamps as the work actually happens:

job.schedule.starts_at       # => 2026-06-26 10:45:00 UTC
job.schedule.ends_at         # => 2026-06-26 12:45:00 UTC
job.schedule.time_zone       # => 'America/New_York'
job.schedule.arrival_window  # => 30, minutes

job.on_my_way_at # => when the pro said they were on their way, or nil
job.started_at   # => when the work started, or nil
job.completed_at # => when the work was finished, or nil

job.created_at   # => 2026-06-21 13:45:35 UTC
job.updated_at   # => 2026-06-21 13:45:36 UTC
job.locked_at    # => when the job was locked against further changes, or nil
job.canceled_at  # => when the customer canceled the job, or nil

Every moment is a Time in UTC, or nil where Housecall Pro has stamped none. job.schedule is itself nil on a job that has never been booked, so reach for it the way you would any other record that may not be there.

What hangs off a job

#

Four of these arrive inside the job Housecall Pro already answered with, so reading them costs nothing more:

job.customer.name  # => 'Ada'
job.customer.email # => 'ada@example.com'
job.address.type   # => :service
job.address.city   # => 'Springfield'
job.notes.map &:content             # => ['Gate code is 4021']
job.assigned_employees.map &:name   # => ['Ada Example']

Three are lists Housecall Pro keeps under the job, and each is a relation of its own — one request, walked lazily:

job.appointments.count     # => 1
job.appointments.first.starts_at # => 2026-06-26 10:45:00 UTC

job.line_items.map &:name  # => ['Exterior trim - Fascia repair']
job.line_items.sum &:amount # => 0.33e3

job.invoices.map &:invoice_number # => ['51575153']

Housecall Pro takes no conditions on any of these three, so they walk, count, limit and find by ID, and they do not where. Each record is documented on the appointments page and the records page.

What a job does not do

#

Housecall Pro takes no PUT, POST or DELETE for a job, so Hcp::Job has no create, no update and no destroy. It reads. The only two writes the gem has are on leads.
